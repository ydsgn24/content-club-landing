# CLAUDE.md

Інструкції для Claude Code при роботі з цим репозиторієм.

## Огляд проєкту

Односторінковий продажний лендинг («Content Club») — платного Telegram-ком'юніті
від Instagram-блогерки Юлі. `index.html` — довгий скрол-фаннел: hero → відео-тизер
→ вміст клубу → аудиторія → відгуки → інтро засновниці → сюжет-заперечення →
Q&A → тарифи → бонус → FAQ → закриваючий CTA → відео-модалка. Весь видимий
контент — російською (`lang="ru"`), написаний у продажному/маркетинговому тоні —
див. розділ «Контент і копірайтинг» перед редагуванням тексту.

## Технологічний стек — без build-кроку

Це **чистий статичний сайт**: вручну написані HTML/CSS/JS, без `package.json`,
без бандлера, без фреймворку, без npm-залежностей, без `node_modules`.
`index.html` підключає кожен CSS/JS файл напряму відносним шляхом.

- Для перегляду: відкрити `index.html` напряму в браузері, або підняти будь-який
  статичний сервер (наприклад `python3 -m http.server`).
- **Не додавати** бандлер, фреймворк (React/Vue тощо), CSS-препроцесор,
  пакетний менеджер чи будь-яку npm-залежність без прямого запиту користувача.
  Нові доповнення мають лишатися в тому самому вручну написаному, без-build стилі.

## Організація файлів

Проєкт використовує принцип **один файл на секцію/компонент** і в CSS, і в JS.
Зберігати цей підхід при додаванні чи редагуванні секцій — не зливати секції
докупи, не розбивати одну секцію на кілька файлів.

- `css/variables.css` — design-токени (кольори) як CSS custom properties.
- `css/base.css` — ресети / глобальні базові стилі.
- `css/components/<секція>.css` — один файл на секцію, названий за секцією
  (`hero.css`, `pricing.css`, `faq.css`, `accordion.css`, …).
- `js/<секція>-<поведінка>.js` — один файл на поведінку, назва
  `<секція>-<поведінка>.js` (наприклад `audience-fit-scroll.js`,
  `faq-reveal.js`, `club-contents-accordion.js`). Одна секція може мати
  кілька файлів-поведінок (наприклад `keyhole-bonus.js` +
  `keyhole-bonus-reveal.js`).
- Нові CSS-файли додаються як `<link>` у `<head>` файлу `index.html`; нові
  JS-файли — як `<script>` ближче до кінця `<body>`, у тій же позиції, що й
  секція в потоці сторінки.

## CSS-конвенції

- Скрізь **BEM**-нотація: `.section`, `.section__element`,
  `.section__element--modifier` (наприклад `.hero__bg`,
  `.pricing__card--3m`). Дотримуватись цього точно для нової розмітки — без
  utility-класів, без інших схем іменування.
- **Використовувати токени з `css/variables.css`** (`var(--color-*)`) замість
  хардкоду hex/rgba значень. `variables.css` документований як 1:1 дзеркало
  Figma-колекції змінних "Colors" (ID файлу в шапці файлу) — якщо потрібного
  кольору ще немає, спочатку додати його туди за тим самим іменуванням, а не
  вписувати інлайном.
- Файли компонентів CSS містять коментарі з посиланнями на **Figma node ID**
  (mobile/desktop, іноді tablet) і точні специфікації макета для кожного
  брейкпоінта. **Figma — джерело істини** для цього сайту — він побудований
  пиксель-точно за дизайном у Figma, а не за загальною responsive-інтуїцією.
  При редагуванні макета:
  - Зберігати/оновлювати коментарі з Figma node ID, щоб вони лишались
    актуальними.
  - Підганяти відступи/розміри під числа з коментарів, якщо є посилання на
    Figma, а не «на око».
  - Деякі файли фіксують свідомі відхилення від Figma (наприклад, відсутні
    експортовані асети, тимчасові шрифти-заглушки — див. `pricing.css`) —
    читати ці нотатки перед тим, як «виправляти» щось, що насправді є
    задокументованим, навмисним пропуском. Зберігати або оновлювати ці
    нотатки, а не видаляти їх.

## JS-конвенції

- Кожен файл — самостійний **IIFE**: `(function () { ... })();`. Без
  `import`/`export`, без спільної модульної системи, без бандлера — кожен
  файл підключається як незалежний `<script>` і має сам себе захищати
  (наприклад `if (!section) return;`), а не покладатись на порядок
  завантаження чи спільні глобальні змінні.
- Перевага **нативним браузерним API** над додаванням бібліотеки:
  - Scroll-анімації появи використовують **Web Animations API**
    (`element.animate()`), а не сторонні анімаційні бібліотеки/фреймворки.
  - Акордеони/модалки використовують нативні елементи `<details>`/`<dialog>`,
    а не кастомні саморобні віджети.
- Не додавати JS-залежність (анімаційну бібліотеку, плагін акордеону,
  бібліотеку модалок тощо) — розширювати наявний IIFE-патерн замість цього.

## Шрифти

Чотири родини шрифтів, підключені чотирма різними способами — зберігати цю
структуру:

- **`KudryashevHeadline-Sans/`** — самостійно хостований, власна папка з
  файлами шрифту (woff2/woff/ttf) плюс `style.css` з `@font-face`. Підключений
  напряму з `<head>` файлу `index.html`.
- **`Classica Two/`** — самостійно хостований, власна папка з `.ttf`,
  `style.css` (`@font-face`, `font-family: 'Classica Two'`) і
  `COPYRIGHT.txt` — це **комерційний/ліцензований шрифт**, тримати файл
  ліцензії поруч і не поширювати шрифт в інших місцях.
- **Jost** та **Parisienne** — завантажуються з Google Fonts CDN через
  `<link>` у `<head>` (без локальних файлів).

Кожна самостійно хостована папка шрифту — самодостатній міні-CSS-модуль
(шрифти + `style.css` разом). **Не переносити файли шрифтів у `css/`** і не
виносити `@font-face`-декларації з `style.css` їхньої папки — патерн
«папка-як-модуль» є навмисним і тримає файли/ліцензію шрифту разом з його CSS.

### `Jost-UA-Patch/` — заповнення українських літер, яких немає в Jost

Google Fonts збірка Jost (жодна вага) не містить і/ї/є/ґ — жодного варіанту
цих літер немає в файлі шрифту взагалі (перевірено по cmap реальних файлів
Google, не за замовчуванням браузера). Оскільки Jost — практично шрифт за
замовчуванням майже для всього сайту, а і/ї/є трапляються 500+ разів у
`index-ua.html`, без цього браузер тихо підставляв системний sans-serif
лише для цих літер посеред слів — помітний розлад стилю в багатьох місцях.

`Jost-UA-Patch/style.css` підключає три `@font-face` (ваги 400/500/600), які
навмисно названі так само `font-family: 'Jost'` — це і є механізм: Google вже
розбиває Jost на кілька `@font-face` за `unicode-range`, і коли жоден з них не
покриває символ, браузер автоматично шукає наступний `@font-face` з тим самим
`font-family`, яким тут виступає файл з цієй папки, обмежений
`unicode-range` саме на і/ї/є (U+0404, U+0406-0407, U+0454, U+0456-0457).

Файли в цій папці — **не нове малювання**, а сабсет самого Jost: і/І взяті з
латинської i/I (та сама форма в цьому шрифті), ї/Ї — з латинської ï/Ï (те ж
розташування крапок), є/Є — з власної кириличної э/Э Jost (та сама
"дзеркальна-Е" літерна родина — підтверджено візуально, mirror(e) ≈ real э).
Немає ґ/Ґ — 0 входжень у поточному тексті, і жодна літера в Jost не апроксимує
її гачок достатньо добре для аліасу; якщо колись знадобиться — треба або
власне малювання гачка, або unicode-range фолбек на інший шрифт.

Jost — SIL OFL 1.1 (ліцензія лежить поруч, `OFL.txt`), яка прямо дозволяє
модифіковані/похідні файли шрифту за умови, що ліцензія йде разом з ними —
звідси й ця папка. **Той самий трюк свідомо НЕ зроблений для `Classica Two`**
— її copyright — голе «all rights reserved» без явного дозволу на похідні
роботи, тож для одного місця, де їй бракує "і" (`.keyhole-bonus__title`,
слово «відкритих»), літера замінена прямо в тексті `index-ua.html` на
латинську "i" (див. коментар над `.keyhole-bonus__title` в
`keyhole-bonus.css`) — а не пропатчений сам файл шрифту.

## Контент і копірайтинг

Весь текст сторінки — російською, написаний у продажному/маркетинговому тоні
(короткі влучні фрази, риторичні питання, акцент на терміновості/вигоді,
неформальне звертання на "ты"). При редагуванні чи додаванні тексту:

- Зберігати наявний тон — не переходити на нейтральний/технічний стиль.
- Не робити машинний переклад чи перефразування англійською — це не
  мультимовний сайт, мова одна.
- Зберігати порядок і структуру секцій воронки, якщо не попросили змінити —
  кожна секція написана так, щоб вести до наступної.

## Горизонтальний overflow ("сайт гуляє по горизонталі") — як діагностувати і фіксити

Сайт активно використовує `position: sticky` для scroll-jack ефектів
(`.keyhole-bonus__pin`, `.what-if__pin`) і декоративні елементи, що навмисно
"випливають" за межі viewport (torn edges, `.site-footer__hand` тощо). Це
поєднання ламається дуже специфічним чином — задокументовано тут, щоб не
повторювати той самий цикл спроб:

- **НЕ виправляти через `overflow-x: hidden` на `html`/`body`.** Per spec,
  non-visible overflow на BODY проброюється на сам viewport/root — це міняє
  саму механіку скролу, а не просто "обрізає вміст". Ламає `position: sticky`
  для БУДЬ-ЯКОГО нащадка на сторінці (перевірено: `.keyhole-bonus__pin` і
  `.what-if__pin` переставали триматися на місці повністю).
- **НЕ виправляти через обгортаючий `<div>` з `overflow-x: hidden`** (навіть
  якщо це не html/body, а звичайний блок). Будь-який предок з overflow
  відмінним від `visible` стає "scroll container" — саме це визначає, відносно
  чого `position: sticky` рахує свою позицію, незалежно від того, html це чи
  ordinary div, і незалежно від того, чи цей контейнер колись реально
  скролиться сам. Ламає sticky так само, як і html/body варіант.
- **`clip-path` — не заміна overflow для цієї задачі.** `clip-path` це
  paint-time обрізка, вона НЕ зменшує `scrollWidth`/можливість
  драгу-скролу сторінки вбік — тільки ховає контент візуально. Використовувати
  clip-path можна, коли треба обрізати ОДНУ вісь без створення scroll-контейнера
  (напр. `inset(-9999px 0)` щоб обрізати X, лишити Y вільним) — але для
  горизонтального "гуляння сторінки" сам по собі він не рішення.
- **Як насправді знайти винуватця:** не гадати по CSS, а виміряти емпірично.
  Playwright (`npm install playwright && npx playwright install chromium` —
  встановлюється локально, білдкроку в проєкті не додає) headless, пройтись по
  всьому DOM від `<body>` вниз, порівнюючи `getBoundingClientRect()` кожного
  елемента з viewport, **пропускаючи піддерева, де предок вже має
  `overflow-x` відмінний від `visible`** (бо такий предок вже коректно все
  обрізає, глибше дивитись не треба). Це миттєво і однозначно вказує на
  справжній елемент (в одному з проходів — `.site-footer__hand--left/--right`,
  а не жоден з "торн-едж" 1440px декорів, які виглядали підозріло, але були
  вже коректно контейнеризовані власною секцією).
- **Правильний фікс для елемента, що навмисно "вилазить" за viewport
  (bleed-декор):** зробити контейнер ЦЬОГО елемента достатньо високим/зсунутим,
  щоб весь bleed (включно з проміжними станами анімації, напр. pre-reveal
  transform) вкладався ВСЕРЕДИНІ власного боксу контейнера — тоді
  `overflow: hidden` саме на цьому контейнері безпечний (нічого не втрачає
  візуально) і не чіпає жодного `position: sticky` десь-інде на сторінці, бо
  не є предком sticky-елементів.
- Після будь-якого фіксу тут — перевіряти емпірично
  (`document.documentElement.scrollWidth === window.innerWidth` на
  мобільному І десктопному viewport), а не тільки візуально/на слово.

## Відомі "хатні" моменти (позначати, не виправляти самовільно)

- **Git-репозиторій ще не ініціалізований.** Якщо просять внести зміни, варто
  запропонувати `git init` (з `.gitignore`) перед редагуванням, щоб зміни
  відстежувались — але не запускати це без запиту.
- **`0720.mov` (~1GB) лежить у корені проєкту** і ніде не підключений в
  `index.html` — схоже на забуте сире відео, не частину задеплоєного сайту.
  Позначити для видалення (або виключення через `.gitignore`), а не видаляти
  самостійно.
- **Імена файлів у `images/` непослідовні** — частина описова kebab-case
  (`hero-photo-1.webp`), багато сирих Figma/російських export-імен
  (`фон Юля.webp`, `отзыв 1.webp`). Це косметична проблема, не баг — не
  робити масове перейменування без запиту; для нових зображень
  використовувати описову kebab-case назву, наявні посилання не чіпати.

## Чого уникати

- Не додавати build-крок, фреймворк чи пакетний менеджер.
- Не рефакторити принцип «один файл на секцію» в CSS/JS у спільні бандли.
- Не замінювати нативні `<details>`/`<dialog>`/Web Animations API на
  бібліотеку "для зручності".
- Не хардкодити кольори, які вже існують як токени в `css/variables.css`.
- Не перейменовувати/реорганізовувати папки шрифтів чи `images/` масово.
- Не перекладати і не переписувати тон копірайтингу без прохання.
